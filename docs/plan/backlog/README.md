## Pythonの静的チェック

Ruffによる検査から型検査、整形の順に導入する。
前のプランを完了記録に解決してから次を開始する。

1. [364：lintと限定した自動修正](364-enforce-bounded-python-lint.md)
   未定義名などを検査し、自動修正は許可した規則と明示したファイルに限定する。
   試行でRuff 0.15.7が5ファイルに報告したF821の13件を、診断として確認したうえで解消する。
2. [365：検証用スクリプトの型検査](365-check-types-in-python-validation-tools.md)
   Pyrightで引数や戻り値の型を検査する。
   3種類のスクリプトとテンプレート側の対応ファイルを対象にし、6ファイルすべてが解析されることを確認する。
3. [366：検証用スクリプトの整形](366-format-initial-python-validation-tools.md)
   同じ6ファイルにRuffのフォーマッターを適用し、整形漏れをローカルとCIで検査する。
   不具合修正とは別のコミットにし、構文木とコメントの保持、再実行で差分が出ないことを確認する。

LSP接続、Python以外のツールの導入、全ファイルの一括整形は、この初期導入には含めない。

前提の資格情報隔離は、355を再構成した[359](../checked/2026/09/01-15/359-isolate-opencode-go-inference-credentials.md)として完了済みである。

1. [356：読み取り専用の調査の委任](356-delegate-read-only-tasks-to-opencode-go.md)
   明示したモデルと入力パスで調査を依頼し、助言として結果を受け取る。
   既定では無効のままにし、要求した設定と実際に観測した実行を別の記録として扱う。
2. [357：実装候補の生成の委任](357-delegate-candidate-implementation-to-opencode-go.md)
   既存の隔離実行を通じて実装候補と修正候補を生成させる。
   既存の試行回数、受け入れ記録、親による検証の条件は変えない。

どちらの完了も、実際のモデルで品質が向上したことを意味しない。

## 別セッションでの同時実装

1プランにつき1セッションと1専用 worktree を割り当て、独立した2件を同時に実装する。
取り込み担当のセッションが、レビュー結果の受け入れ、最終検証、元ブランチへの反映、完了処理を順番に行う。
次の3件はこの仕組みを作るためのプランであり、既存の手順で順番に実装する。

1. [372：セッションの所有管理と専用 worktree への結び付け](372-bind-parallel-plans-to-separate-session-owners.md)
2. [373：各セッションでの実装、修正、取り込み担当への引き渡し](373-run-parent-direct-plans-in-member-sessions.md)
3. [374：先行変更を含めた取り込み、完了処理、実セッションでの確認](374-publish-and-verify-separate-session-plan-results.md)

374は、模擬テストに加えて2つの実セッションでの作業、両方の変更の保持、完了した worktree と一時ブランチの削除を確認するまで完了にしない。

## 昇格するときの確認

実装を開始する際は、進行中プランの枠が空いていることと、各プランの前提作業が完了していることを確認する。
前提作業への参照は、`docs/plan/checked.md`から実在する完了記録に解決してから昇格する。
現在activeにある[360](../active/360-resolve-multigeneration-lineage-rebinding.md)の状態は、この確認では変更しない。

いずれのプランも、既存の必須検証を保つことと、生成済みプロジェクトの更新で製品コードやプロジェクト所有の設定を保持することを完了条件に含める。
