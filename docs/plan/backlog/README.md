# 改善プランのバックログ

前回の調査で挙げた改善点を、六つの実装プランに分けた。
軽量な変更手続の指摘は、ファイル数による分類と完了条件の分割不能という独立した二件に分けている。

現在の実行対象はプラン 268 のままとし、この一覧の追加では切り替えない。
以下は未着手のプランであり、改善の実装や性能測定が完了したことを示すものではない。

| プラン | 対応する指摘 | 実装する変更 | 着手条件 |
| --- | --- | --- | --- |
| [272](272-count-mirrored-mechanical-edits-as-tier-zero.md) | root/template の同期義務により機械的な小変更が Tier 0 から外れる | 既存の一組へ同じ機械的編集を行う場合だけ例外にする | 既存の実行を切り替えず、着手時に現在の規則を確認する |
| [273](273-stop-indivisible-tier-one-work-without-descope.md) | 完了条件が一件の Tier 1 に、二つへの分割を要求している | 条件を保持した停止手順と、新規受入時の一件制約を整える | 268 が完了している |
| [274](274-preserve-project-owned-agent-model-settings.md) | Copier 更新が利用側のモデル設定を上書きする | 既存値を保持し、欠落項目だけ補う | 更新処理と差分検査を同じ変更で直す |

| [276](276-run-bounded-parent-owned-candidate-preflight.md) | worker の候補生成とテスト結果の間に短い確認手順がない | 親が候補生成後に隔離テストを一回実行し、既存の訂正へ結果を渡す | 268、275 の完了と、利用者による設計承認 |

## 実行順と境界

プラン 268 の完了後は、272、273、274、275 の順に進めると、変更済みの規則を再配置する際の衝突を避けやすい。
277 はこれらから独立しており、276 より先に実装すると、以後の作業で観測できる項目を確認できる。
276 は隔離実行と訂正手順に関わるため、後段で独立レビューを伴う親実装として扱う。

依存先がまだバックログにある間は、各プランの `integration_gates` に着手条件を記す。
昇格時には依存先の完了記録を確認し、必要な `predecessor_plans` と参照先を確定する。
これはプランの再構成による後継関係ではなく、通常の実行順序である。

六件とも規則、検証定義、更新時の所有権、または隔離実行に関わるため、変更自体は Tier 2 とする。
272 が将来認める Tier 0 の例外を、272 自身の実装には使わない。

275 と 276 は設計判断を含むため、review class C の承認待ちとしている。
今回のプラン作成依頼を、その設計の承認としては記録しない。

プラン 192、193、194 の保留解除、新しい大規模評価基盤、モデルの自動変更、検証の省略は含めない。
少資源環境の実行基盤を新設するプランも追加せず、今回確認できた既存機構の具体的な不整合と不足に範囲を限定する。

## 維持する仕組み

変更範囲の限定、親による受入、隔離環境での検証、独立レビュー、訂正回数の上限、正式検証失敗後の診断停止を維持する。
Copier による非破壊更新、root/template の整合検査、ローカルログの保存境界も維持する。

廃止する対象は、小変更を妨げる二つの不整合、既存モデル設定の強制上書き、入口での詳細規則の重複である。
安全条件そのものを廃止するプランではない。
