# 開発手続きの改善プラン

前回の調査と2026年9月8日の作成指示に基づき、既存五件を維持し、未収録だった四件を追加した。
この一覧は計画と実行順の説明であり、実装や時間短縮が完了したという報告ではない。
実装開始を指示されたプランを、公開済みの状態から一件ずつactiveへ昇格する。
今回の作成では実行中のプランを追加しない。

## 今回の作成範囲

新規四件は、フックのコマンド解釈、プラン一覧の生成、既存スキルの判断手順、親による実装の開始準備に分ける。
いずれも製品コード、配布するスキルまたは規則を変更する実装プランであり、調査だけのプランは作らない。
検証定義、規則または実行管理に触れるため、新規四件のimplementation_tierは2とした。
今回作成する計画文書はこのリポジトリ固有の作業記録であり、テンプレートへ複製しない。
各実装プランのwrite_scopeには、必要なroot/templateの対応先を含めている。

新しい要件、権限拡張、停止済み実行の継続は、それぞれ既存の承認規則を適用する。

## スキルへまとめる判断

新しいスキルは追加しない。
299でdecision-auditの直接参照資料へ共通判断を集め、implementation-guidelinesとsequential-plan-orchestratorから該当作業のときだけ参照する。

- 依頼が製品の修正か、開発手続きの改善かを区別する。
- 承認済みの要件と判断を使い、変更がないものを再承認に戻さない。
- 長文の計画より先に、既存の作成コマンドで要件と変更先と検査の対応を確認する。
- 修復を計画する前に、失敗した実際の操作を再現する。
- 停止状態、レビュー回数、外部効果の権限は既存仕様へ戻って判断する。

規範をスキルへ移して別の正本にしない。
規則の移動は275、既存スキルへの具体的な判断手順の追加は299として分ける。

どちらも他方の完了を必須条件にしない。

## 効果の確認

プラン数や規則数が増えたことを改善成果とは扱わない。
取得できた作業時間、候補生成と訂正の回数、検証回数、停止理由を277で表示する。
利用者の介入や待ち時間が記録から直接分からなければ、未観測のまま残す。
104では誤拒否を再現するケース、298では実在するリンク、299では固定した判断例、300では準備操作と途中失敗を、各プランの正しさの証拠にする。
