# 別セッションで別プランを並列実装するための計画

別々の会話セッションで独立した2件のプランを実装し、両方の変更を保持したまま対象ブランチへ反映して完了できることを確認する。
既存の実装と引き渡しの仕組みを使い、統合レビュー、正式な完了処理、実セッション証拠の検証の不足を先に実装する。

今回の成果は計画作成までであり、実装、実セッションの起動、実行グループの登録は行っていない。
[385：実セッション証拠の検証](backlog/385-verify-live-session-distinctness-from-bound-transcripts.md)を未着手のbacklogへ戻した。
[402：統合レビューの接続](backlog/402-connect-post-handoff-review-to-exact-assembly.md)と[403：統合担当による完了処理](backlog/403-complete-published-session-members-through-integration.md)を新規のbacklogとして作成した。
402と403は設計承認待ちであり、この文書だけでは実装を開始しない。
この文書は実施順序と実地確認の条件を定める運用計画であり、番号付きプランや停止した実行を再開する許可ではない。

## 達成する動作

- 実装担当AはプランAと専用worktreeだけを変更する。
- 実装担当BはプランBと別の専用worktreeだけを変更する。
- AとBは別の会話セッションとして起動し、両方の実装期間に重なりがある。
- 統合担当はA、Bとは別のセッションとプロセスを使う。
- 統合担当が一件ずつレビュー、検証、対象ブランチへの反映を行う。
- Bの反映後もAの変更が残り、完了した各タスクのworktreeと一時ブランチがなくなる。
- 結果は実際のトランスクリプトとGitの内容から確認できる。

対象は2件の独立したプランに限定する。
3件以上の同時実行、同じファイルの同時編集、未完了の相手の成果に依存する実装、リモートへのpush、任意のCLIのトランスクリプト形式への対応は追加しない。
共有の実行制御、受け入れ条件、検証権限をメンバー自身に書き換えさせない。

### 2. 実地確認用のプロジェクトと2件のプランを準備する

402、403、385を含む受け入れ済みコミットを固定し、そのテンプレートから隔離されたローカルの生成プロジェクトを作る。
このリポジトリの実行制御を、並列作業の対象にはしない。
実地確認用のGitリポジトリ、対象のローカルブランチ、認証情報を含まない正規形式のorigin、証拠の保存先を開始前に確定する。
ネットワークへの書き込みは行わない。

各メンバーには、実際に製品コードを変更する小さなプランを割り当てる。
実地確認の標準ケースは、独立した次の2つのコマンドを持つ小さなPythonプロジェクトとする。

| 担当 | 実装する振る舞い | 変更範囲 |
| --- | --- | --- |
| A | 標準入力の論理行数を出力する。空入力は0、空行も1行、末尾改行の有無で最後の行を落とさない | `src/line_count.py`、`tests/test_line_count.py` |
| B | 標準入力の重複行を除き、最初の出現順を保つ。空入力、空行、同じ行の連続と離れた重複を扱う | `src/unique_lines.py`、`tests/test_unique_lines.py` |

両方のプランの仕様と検証条件は準備時に確定し、メンバーは互いの製品コードやテストを読み込みに依存しない。
共通の初期設定と検証コマンドは、メンバーが始める前に統合担当が用意する。
共有設定や同じテスト登録ファイルを双方の変更範囲に入れない。
個別の検証は各担当のテストを実行し、統合後には両方のコマンドを実際に起動して出力を確認する。

生成プロジェクトの正式な計画作成コマンドを使い、IDを共有ロックの下で採番する。
計画記録だけを変更する実証専用プランは作らない。
2件の製品変更、受け入れ条件、検証入力が独立していることを確認してから、schema 2、各メンバーの `implementation_mode: parent_direct`、2件だけの構成を登録する。
両プランと実行グループ定義を先にコミットし、共通の開始コミットを固定する。

実地確認の義務は、製品変更を持つメンバープランの一方に、両メンバーの反映と証拠確認を求める受け入れ条件として追加する。
その条件のSHA-256を `live_evidence_acceptance_sha256` に記録し、`live_evidence_contract: parallel_sessions_v1` とともに、実行台帳を作る前に確定する。
そのプランを先に完了扱いにせず、両方の反映後に実地証拠を検証してから完了させる。
新しい義務を作り、棚上げ382の非公開記録を流用したり、旧379の台帳を再開したりしない。

### 3. 実際の別セッションで実装する

利用者が実装担当A、実装担当B、統合担当の3セッションを起動する。
`scripts/run-parallel-plans.py` はエージェントを起動するコマンドではないため、存在しないセッションIDや子プロセスを作って実証の代わりにしない。

生成プロジェクトでは、以下のコマンド名の前に `.project-agent-workflow/` を付けた配布先を使う。
実行時のパスとIDは、そのコマンドが返した値を受け渡す。

1. 統合担当が `parallel-plan-state.py session-state-path` と `group-init` で、正規のグループ状態と自身の実セッション、祖先プロセスを結び付ける。
2. AとBがそれぞれ、自分の実セッションから `run-parallel-plans.py member-start` を実行する。
3. 各担当は、コマンドが返した自分のworktreeだけで作業する。
4. 各担当の台帳を `plan-execution-state.py prepare-parent-direct --group-state` で準備し、既存の実行前確認を通す。
5. 実地確認の義務を持つプランでは、最初の製品変更より前に `verify-parallel-plan-sessions.py init --plan ... --execution-state ... --group-id ...` で証拠を予約する。
6. AとBが同じ期間に実装し、各自のテストと実際のコマンド出力を確認する。
7. 各担当が `member-ready` で結果を固定し、統合担当へ引き渡す。
8. 引き渡し後はトランスクリプトを保存し、利用者が各メンバーの実プロセスを終了する。
   統合担当は、登録された正確なプロセスが終了したことを確認してから、そのメンバーの結果を反映してworktreeを退役させる。

セッションID、プロセスの生存と祖先関係、トランスクリプトの取得を確認できない場合、製品編集を始めない。
両担当の実装中のツール実行をトランスクリプトに残し、単に二つの端末が開いていた時間を重なりとしない。
引き渡し後のメンバー編集、同じタスクへの二重の担当、終了していないセッションからの引き継ぎは行わない。
再開が必要な場合も、停止の証拠と既存の `member-resume` を使い、試行数やレビュー数を初期化しない。
会話の一つのターンを終えるだけでは、プロセスの終了とはみなさない。
`member-ready` もプロセスを終了しないため、生存したままの反映によって「反映済みだがworktreeを削除できない」状態を作らない。

### 4. 統合担当がA、Bの順に反映する

統合担当が `run-parallel-plans.py assemble --handoff` でAの結果を現在の対象ブランチに組み合わせる。
その正確な変更を独立レビューし、指定された検証を実行する。
対象ブランチが変わっていないことを確認し、専有された反映権限の下で `publish` を実行する。

Bも同じ手順で反映するが、組み合わせる基準はAを反映した後の対象ブランチとする。
Aを反映する前の検証結果を、そのままBの最終結果の検証とみなさない。
レビューは402で統合経路へ接続した384の証拠付き記録を使い、グループへの件数記録だけでレビュー完了としない。
正式な入口が拒否した場合、台帳やグループ状態を手で書き換えて先へ進めない。

対象ブランチへの反映、完了処理、worktreeと一時ブランチの削除は、統合担当が一件ずつ行う。
正式な完了とアーカイブは403で追加する統合担当の経路を使い、専用の統合タスクworktreeで共有索引を更新して、その文書変更も正式に反映する。
すでに削除したメンバーのworktreeや、元のチェックアウトを直接編集して完了処理を代替しない。
メンバー自身に反映や完了の権限を渡さない。
Bが失敗しても、受け入れ済みのAを取り消したり、Bの未反映変更を捨てたりしない。
中断した場合は既存の `publish-recover` が扱える範囲だけで復旧し、結果が不明なら未完了として残す。

### 5. 実地証拠を検証してから完了を報告する

各トランスクリプトは、プロジェクトと両worktreeの外に置いた非公開のコピーを使う。
生ログ、レポート、証拠予約、台帳はGitへコミットしない。
レポートには、385で確定した各メンバーの証拠フィールドと、引き渡し時のGit情報を記録する。
証拠の時刻は実際の記録から確認し、重なりがあるように書き換えない。

統合担当が次のすべてを確認する。

- [ ] トランスクリプトが2つの異なる実セッションを示し、実装期間が重なる。
- [ ] 両方の製品変更が各自の受け入れ条件を満たす。
- [ ] A、Bの順で対象ブランチに反映され、Bの後にもAの変更が保持される。
- [ ] 最終ブランチの各ファイルの内容、モード、削除の有無が、引き渡し時の結果と一致する。
- [ ] 完了した各タスクのworktreeと一時ブランチがなく、必要なローカル証拠が残る。
- [ ] `verify-parallel-plan-sessions.py verify --plan ... --report ...` が成功する。
- [ ] `bind` と `require` が成功し、正式な完了判定が通る。

`PROJECT_AGENT_WORKFLOW_PARALLEL_LIVE_REPORT` や `PROJECT_AGENT_WORKFLOW_REQUIRED_EVIDENCE` に頼らず、正規の証拠予約と明示したレポートで確認する。
385の自動試験に使う合成トランスクリプトは、正常系と拒否条件の回帰確認に限る。
それをこの実地確認の証拠として提出してはならない。

## 停止する条件と完了の区別

402、403、385で範囲外の変更、未解決のHighまたはMedium指摘、正式検証の失敗が出た場合、既存の停止と診断手順に従う。
実地確認でセッションの結び付け、証拠、反映、完了処理のいずれかが成立しなければ、並列開発を実証済みとは報告しない。
エラーのコマンド、基準コミット、未反映の変更、残ったworktree、証拠の所在を残す。
この運用計画を根拠に、停止済みの実行枠を増やすことはできない。

今回の計画書作成、402、403、385の各実装完了、実地確認の成功を、別々の結果として記録する。
既存の自動試験が通るだけでは、実地確認を完了にしない。
実証後も、通常の開発では2件の独立性を登録して確認し、統合と反映を直列にする条件を維持する。
