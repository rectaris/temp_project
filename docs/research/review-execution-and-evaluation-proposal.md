## 既存実装で確認した接続不足

以下はローカルsource `4a24454a7349671341e478dc2af1d9ab4522823a` の読取り調査であり、公開基点への配布や実サービスの動作を示すものではない。

この文書では、それらの変更を実施したとも、正式レビューの捕捉不足を解消したとも主張しない。

## レビューで確認する対象

確認する対象は、同じsourceと候補に結び付いたレビュー要求、dispatch、起動、読取り、結果、親の判断の記録である。
指定された差分と条件を、読取り専用の実行主体が実際に調べたかをその記録で確認する。
起動要求、実起動、読取り、結果、受入は別の事実である。
成功した起動要求、profile名、結果JSON、文章内の「読んだ」という申告だけでは、実起動や読取りを証明しない。

| 段階 | 既存記録に結び付ける内容 | それだけでは証明しないこと |
| --- | --- | --- |
| 親の要求 | `review_id`、`run_id`、task/planの識別子、対象source・差分・仕様のdigest、要求したbackend/model | 実行開始、実際のモデル |
| dispatch | 実際に選んだbackendと起動境界、要求への参照、観測元 | session開始、sandboxや読取りの実施 |
| 実起動と終了 | controllerまたはruntimeが観測したprocess/session、開始、終了、exit、timeoutまたはunavailability | モデル実行、対象を読んだこと |
| 読取り | 観測した操作名、限定したpath/symbol/range、結果、対応する証拠への参照 | runtimeが公開しない操作、返答内容の正しさ |
| 結果 | 実行への参照、対象digest、各指摘の根拠、result artifactのdigest、未確認事項 | 受入、正式レビューの成立 |
| 親の判断 | 検証した証拠への参照、受入または拒否、残る指摘、既存の条件との対応 | 必須検証の代替、続行や公開の追加権限 |

既存の識別子と記録への参照で表せる情報は、重複保存しない。
不足する相関情報を追加する場合も、必要な識別子、digest、観測元、結果に限定する。
生のprompt、コメント本文、source本文、環境変数、credentialを、新しいイベント欄へ保存しない。

要求したbackend/modelと、実際に観測したbackend/modelは分ける。
実行ファイルの版とdigestは、そのファイルを識別するものであり、providerが実行したモデルを証明しない。
profileの設定や結果の文体から実モデルを推定しない。

## 観測不足と正式レビュー

観測元がない事実は `not_observed` とする。
起動が起きなかったことを直接示す記録がある場合に限り、不起動と記録する。
失敗した実行と、実行したか分からない状態を混ぜない。
runtimeが読取りを公開しない場合は、その制約を明示し、レビュー文章から操作履歴を補わない。

正式レビューには、現行の入口が要求するsource、対象差分、仕様、session、packet、receiptの対応をそのまま必要とする。
この案の相関情報やSDKの助言結果で、その条件を置き換えない。
対象変更後の指摘が古い差分への指摘を参照していないか、結果の実行元が要求と一致するかを親が確認する。
同じ実行の結果を別のreviewとして再利用しない。

出所を確認できない結果は助言として保持し、正式レビューを完了したとは扱わない。
指摘がある場合は、その反例、対象、未解消の条件を残す。
HighまたはMediumが未解消なら受入しない。

## 修正開始と再レビュー

調査する対象は、元のplan、候補、停止理由、lineage、消費済み予算、所有者の承認に結び付いた既存の修正開始処理である。
元のplan、候補全体とartifact/digest、停止理由、指摘、検証失敗、correction lineage/epoch、消費済み予算、承認の適用範囲を引き継ぐことを確認する。
単に変更先が許可されたことと、停止した実行を再開できることは別である。

正常系は、承認済み開始、実レビュー、指摘、履歴を保持した同一planの修正、再レビュー、独立検証、全候補の受入までを接続して確認する。
どの遷移も、現行controllerの入口と承認に従う。
同一planの限定続行や開始時の承認再利用を、未実装の機能として作り直さない。

scope逸脱、停止理由の不一致、期限や回数の超過、履歴欠落、実行や読取りの出所不足は、それぞれ既存の停止経路へ戻す。
authoritative validationの失敗は既存の `diagnosis_required` を記録し、確認済みの独立診断なしに修正へ進めない。
実装の不具合と、要件・安全条件・権限境界の変化を同じ修復として扱わない。
新しいplan、session、台帳、差分digestで消費を初期化しない。

この文書は、一律のレビュー上限を変更する提案を採用しない。
必要な再レビューの判断と、現行の実行枠へのadmissionを分ける。
既存上限の変更は、独立した仕様・制御の受入と所有者による運用採用を要し、保存済み履歴に遡及させない。

## 最小限の受入確認

合成例はadapterや検証処理の試験に使い、実レビューを実行した証拠にはしない。
現在の入口が許可する範囲で、一つの実起動、限定した読取り、対象に結び付いた結果、親の判断を通して観測する。
その入口が成立しなければ未実証とし、結果を捏造したり、別の実行器へ自動で切り替えたりしない。

| 確認する事例 | 必要な結果 |
| --- | --- |
| 許可された実レビュー | 要求、観測した起動、読取り、結果、親の判断が同じ対象へ結び付く |
| 起動前の拒否、timeout、unavailability | 観測した段階と失敗を保持し、完了と混ぜない |
| 読取り記録がない | 読取りを未観測とし、正式レビュー条件を満たしたと扱わない |
| 識別子または対象digestが異なる結果 | 対応を拒否し、元の対象と履歴を保持する |
| 結果だけを差し替えたもの | 検証可能な実行への結合なしに正式結果へ昇格しない |
| 過去の候補や停止理由と合わない修正要求 | 既存の開始条件で停止し、候補や予算を初期化しない |
| lineageまたは消費済み予算の履歴を意図的に省いた要求 | 欠落を検出して停止し、元の候補と履歴を保持する |
| 失効した承認、対象やscopeが異なる承認 | 適用を拒否し、別の開始経路や新しい予算で代用しない |
| 指摘後の同一plan修正 | 指摘前の全候補、消費、承認を保持して再レビューと受入へ接続する |

## 評価の三つの対象

固定した比較可能な入力についての成果物評価、実行観測、反復結果の記録を、Issue #15の区分とPlan 319の比較処理で扱う。

| 区分 | 評価する対象 | 留意点 |
| --- | --- | --- |
| Static outcome | 独立環境の成果物、patch、answer、受入条件、test、scope・API・不変条件 | 実検証した項目と主観的なrubricを分け、項目ごとの証拠を保持し、graderと重みを版管理する |
| Dynamic execution | 直接観測した時間、model/tool call、token/cost、retry、介入、レビュー実行の各段階 | bytesからtokenを復元しない。欠測は `not_observed` のままにする |
| Aggregate reliability | 反復の成功・重大失敗、分布、対応のある差、不確実性、coverage | timeoutやunavailabilityを除外せず、同じ重大失敗を重複減点しない |

記録された失敗は成功率の分母に残し、記録されなかった予定の実行は欠測として区別する。
timeoutで観測した時間は打ち切り時刻までの時間であり、完了時間ではない。
現行のCodexのprocess開始から終了までと、OpenCodeのbackend呼出しから返却までの測定は境界が異なる。
同じ測定境界と比較条件を確立せずに、実行効率や元要求から受入までの時間の差と扱わない。
部分的な観測や通貨不一致で計算された比率を、基準100の比較可能な指標へ昇格させない。
digestの一致は記録同士の整合性を示すものであり、出所の真正性を単独で保証しない。

Outcome Quality、Execution Efficiency、Operational Reliabilityを別々に示す。
任意の合成指標は記述的な補助であり、重みを事前に固定し、安全・品質条件やPlan 319の採用判断を上書きしない。

基準を100とする相対指標は、絶対的な品質点や満点ではない。
Issue #15の `CanonicalBaseline` は、具体的なRunConfiguration、suite/cases、environment/cache、scorerと重み、sample runs、resolved digestsに固定する。
比較可能な観測値だけを使い、基準が0、分母が0、欠測、case coverage不一致などで定義できない指標は未定義と表示する。
生の測定値、区分ごとの結果、pairing、不確実性を残す。
現行productionとの相対値を追加する場合も、過去の基準を書き換えない。
モデルとharnessが同時に異なる比較を、モデル単独の効果と結論付けない。
同一モデルへのアクセスが実際に可能な場合だけ、四つの組合せで影響を分ける比較を検討する。

## 実作業の負担への効果

Issue #17では、元要求から全候補の受入までを一つの作業として確認する。
実装・修正、承認待ち、手続き修正待ち、再レビュー・再構築、追加の運用・保守負担を、観測できる範囲で分ける。
起点や待ち時間の記録がなければ、後から推定した時間を実測として使わない。
指摘や再構築が減ったことだけでなく、必要な停止を守り、候補全体が受け入れられたことを確認する。

既存のPlan 277の集計とIssue #15の評価に適合する観測を再利用する。
合成例、単体試験、文書、接続機能の完成だけで、生産性の改善を主張しない。
比較条件が成立しなければ効果未確認とする。
避けられた見落とし、保証範囲の外、接続不足、実装不具合、前提不成立を、事例の証拠に従って分ける。
同種の問題が再発したかも確認し、効果と追加負担の証拠に基づいて施策の維持、縮小、置換、取り止めを判断する。
いずれの場合も必要な品質・安全条件を維持する。
