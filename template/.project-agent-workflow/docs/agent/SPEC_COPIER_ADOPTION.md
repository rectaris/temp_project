# Copier Adoption

## Purpose

This specification keeps future `copier update` runs predictable by separating files that Copier replaces from files that the generated repository owns.

## Ownership Model

`.project-agent-workflow/` is the template-managed core.

Copier may replace content under that directory during an update, so project-specific facts and local customizations must not be stored there.

`docs/agent/`, `docs/plan/`, root `AGENTS.md`, root `README.md`, `.gitignore`, `.codex/config.toml`, and `.codex/hooks.json` are project-owned after their initial creation.

Those paths are listed in `_skip_if_exists`, so later updates create a missing seed but do not overwrite an existing file.

`.project-agent-workflow/ownership.yaml` is the machine-readable ownership inventory generated into every project.

## Bridge Files

A bridge file is a small host-discovered file that points to the managed core without duplicating its policy or implementation.

- Root `AGENTS.md` routes agents to `.project-agent-workflow/AGENTS.md` and project-owned policy.
- `.agents/skills/*/SKILL.md` routes Codex skill discovery to the corresponding managed skill.
- `.codex/hooks.json` routes enabled project hooks to `.project-agent-workflow/hooks/`.
- `.codex/hooks/*.py` preserves legacy path compatibility; the legacy Stop bridge is deliberately non-blocking.
- `.codex/agents/*.toml` and the dedicated GitHub workflow are host integrations that remain Copier-managed.

Keep bridge content stable.

Add project behavior in project-owned files instead of expanding a bridge.

## Project Extension Points

Store repository-specific policy, domain facts, deployment facts, and validation notes under `docs/agent/`.

Store active, backlog, checked, and handoff state under `docs/plan/`.

Store project-specific skills under `.agents/skills/` using names that do not collide with the generated generic skills.

Add product CI in a separately named workflow; `.github/workflows/project-agent-workflow.yml` validates only the agent-workflow files.

When a project needs a new reusable adapter, keep the project adapter outside `.project-agent-workflow/` and call it from project-owned policy or validation configuration.

## Initial Copy

1. Run `copier copy` with the intended answers.
2. Commit the generated baseline before adding product-specific policy.
3. Add project policy only through the extension points above.
4. Run the generated workflow validation and repository-specific validation.

## Updating an Adopted Project

1. Commit or otherwise preserve the current project changes.
2. Run `copier update` without force-overwriting local conflicts.
3. Confirm that project-owned files are unchanged.
4. Search for `*.rej` files and inline conflict markers.
5. Run `.project-agent-workflow/scripts/migrate-legacy-template-files.py` only when migrating a project generated by the pre-namespace layout.
6. Run `.project-agent-workflow/scripts/validate-changes.py --all` and the repository-specific validation suite.
7. Review and commit the update as one scoped change.

Changes made directly inside the managed core are unsupported extension points and may conflict during an update.

Move such changes into a project-owned extension before the next update.

## Migrating the Pre-Namespace Layout

Repositories generated before this ownership model may contain generic policy under `docs/agent/`, workflow helpers under `scripts/`, and generic skills under `.codex/skills/`.

Treat the first update to the namespaced layout as a one-time adoption migration rather than an ordinary update.

Run `copier update --trust --vcs-ref v1.0.0` when crossing from a v0 release because Copier requires explicit trust before it will execute the versioned migration.

The pre-migration moves legacy generated files into `.project-agent-workflow-migration/v1-pre-namespace/` before Copier can delete their old paths.

Render the new template into a temporary directory, compare each legacy same-path file, and preserve stronger project rules under `docs/agent/` or another project-owned extension.

Do not delete a modified legacy file automatically.

The migration helper may remove only legacy artifacts that it can identify safely and otherwise must stop with a manual-review message.

After the bridge files route to the managed core and legacy duplicates are resolved, later Copier updates should touch the managed namespace and host projections without rewriting project state.

## Conflict Handling

Copier may represent a conflict with inline conflict markers or a `*.rej` file.

Treat either form as unresolved.

Before committing an update, inspect every rejection, preserve project-owned behavior, run `git diff --check`, and run the validation matrix.

## External Services

Generated external-service state is documentation-only by default.

A project may enable read or write behavior only through project-owned `docs/agent/external-services.yaml` and any required project adapter.

`documented` does not authorize external reads or writes.
