# Orchestration

The main agent owns interpretation, final integration, validation acceptance, planning updates, commits, and completion reporting.

## Proactive bounded delegation

- Delegate repository-wide work proactively without waiting for a per-task user instruction only when bounded, independent helper work produces independently useful output and its expected context reduction, parallelism, or review value exceeds coordination cost; repository breadth alone is insufficient.
- Trigger proactive delegation when at least one applies:
  - multiple independent code or documentation areas are affected,
  - cross-specification reconciliation is required,
  - validation, security, or orchestration review crosses several policy areas,
  - large or dense sources benefit from parallel bounded context reduction and expected return justifies the overhead.
- Keep delegation bounded:
  - use explicit `write_scope` per helper,
  - keep helper write scopes non-overlapping,
  - keep context files read-only,
  - require an explicit acceptance note before the main session integrates results.
- Keep non-delegation as the default for short deterministic commands, direct user clarification, and local tasks where coordination cost exceeds expected benefit.
- Keep authorization decisions and final high-risk judgment in the main session.
- Keep secrets, external writes, destructive operations, and authorization actions outside delegated authority unless a separate explicit policy grants that authority.

## Non-delegation boundaries

- Do not delegate short deterministic commands, direct user clarification, final interpretation, final validation acceptance, commit/release decisions, or final report generation.
- Do not delegate work involving external writes, secrets, secret handling, destructive operations, authorization decisions, or final high-risk policy or architectural judgment.
- The main session must reconcile findings and decide what is accepted before planning updates and commits.
- Final report transparency is mandatory: state whether helpers were used, and when used, each helper's role and write scope plus the main-session acceptance rationale.

## Helper Roles

- `repo_explorer`: read-only file discovery and impact analysis.
- evidence_synthesizer means a read-only helper that compares multiple repositories, logs, specifications, implementation alternatives, or cause hypotheses and reports agreements, contradictions, impact boundaries, unresolved questions, confidence, and source evidence for parent verification.
- `fast_scoped_worker`: fast, low-ambiguity code changes with explicit write scope and predetermined validation.
- `scoped_worker`: bounded implementation with explicit write scope.
- `change_reviewer`: read-only correctness, regression, validation, and security review.
- `docs_researcher`: read-only external or version-specific research.
- `sequential_plan_worker`: read-only implementation contract for exactly one assigned active plan; writable execution must route through `scripts/run-sandboxed-plan-worker.py`.

## Delegation Rules

- Delegate only concrete, bounded, independently useful work.
- Assign non-overlapping write scopes.
- For writable sequential active-plan implementation, use `scripts/run-sandboxed-plan-worker.py run` and `scripts/run-sandboxed-plan-worker.py apply`; the worker sees a read-only clone with writable shadow mounts only for normalized, exact file paths in `write_scope`. Directory prefixes, the active plan, the runner, context/spec inputs, and validation-authority paths fail before worker start. An exact missing non-authority path may declare one new file only when its existing parent is a regular in-repository directory. Do not grant direct repository write access to the built-in `sequential_plan_worker` profile.
- Require each writable delegated plan to declare exactly one nonblank `primary_invariant` and the repository to have a canonical `https`, `ssh`, or `git` network `remote.origin.url`. Hash its credential-free canonical host and repository path as the stable repository identity. For every initial, fallback, custom, or correction attempt, derive one bounded versioned contract from the exact committed active-plan bytes and bind it to that repository identity, source HEAD, plan path and digest, run id, and attempt lineage. Validate its exact schema, size, paths, digests, identity, lineage, and fresh equality immediately before invocation, then expose it read-only. The worker reads the contract first and then reads the named active plan and normative inputs directly; the projection cannot override, omit as satisfied, or amend those sources.
- Produce one versioned worker completion receipt inside each initial, fallback, custom, or correction attempt output boundary, including failed attempts before a candidate exists. The worker writes only a bounded exact-shape claims object: acceptance digests with `satisfied` or `not_satisfied`, derived positional command identifiers with observed integer exit statuses, fixed allowlisted blocker and residual-risk codes, and an explicit out-of-scope boolean. The runner rejects free-form bodies and identifiers that could retain prompts, commands, raw output, environment values, credentials, logs, patches, or host paths; malformed claims become a sanitized failure receipt and cannot erase the separately persisted bounded parent-owned process-result artifact with exit status, diagnostic codes, and stdout/stderr digests.
- Assemble and verify the final receipt from parent-known facts: the credential-free repository identity, source HEAD, normalized plan path and digest, verified worker-contract digest, orchestration run id, fresh unpredictable attempt id, correction round and prior-manifest lineage, plus the Git-derived sorted changed paths and candidate patch digest whenever a patch artifact is emitted, including a worker-reported failure. Enforce exact fields, version and byte/value/item bounds, normalized non-symlink paths, fresh identity and lineage, digest cross-links, candidate consistency, process-result consistency, and consumed-attempt replay rejection. A same-run retry receives a different parent-created attempt identity, so a receipt replay fails the manifest-bound attempt check. Missing, duplicate, unknown, malformed, oversized, stale, escaping, deceptive, or inconsistent content fails closed before candidate admission.
- Receipt claims are advisory only. The parent independently derives changed paths from Git, inspects the admitted diff and critical invariants, selects validation from unchanged parent-owned plan data, and exclusively owns lifecycle transitions, validation acceptance, apply, commit, archival, and completion reporting. A worker claim of success, test passage, scope compliance, or acceptance coverage never advances candidate or plan state.
- Admit one writable candidate only as an admissible implementation slice: one invariant that is independently reviewable and validatable and has an explicit later integration gate. Split a broad active plan before delegation rather than using its breadth as a candidate boundary.
- Read optional scalar `implementation_risk` and `implementation_ambiguity` as `low`, `ordinary`, or `high`. Only an absent field defaults to `ordinary`; a present blank, whitespace-only, list-valued, or unknown value fails closed.
- Use Spark medium only when both inputs are `low`; use Terra medium when neither is `high` and at least one is `ordinary`; refuse writable delegation when either input is `high`.
- Preserve explicit nonblank preferred-model, preferred-reasoning, fallback-model, and fallback-reasoning overrides, but reject Sol as both a preferred and fallback writable model. Sol remains reserved for independent security and regression review.
- The sandboxed sequential runner starts the qualified model selected above, or a qualified explicit override, as its preferred attempt. For the default classifier, that model is `gpt-5.3-codex-spark` with medium reasoning for `low`/`low` and `gpt-5.6-terra` with medium reasoning for an eligible `ordinary` input. Only a bounded Codex CLI error line for a usage limit, rate limit, unavailable model, or denied model access may trigger one fallback to `gpt-5.6-luna` with max reasoning.
- A fallback attempt must use the same committed source HEAD in a new isolated clone, scratch directory, writable-shadow set, staged authentication copy, and ephemeral Codex session. Do not reuse worker changes, Git configuration, caches, or output files from the preferred attempt.
- Authentication, network, refusal, implementation, validation, sandbox, custom-worker, and unclassified failures stop without model fallback. Keep every attempt's raw output local and record only bounded provenance and digests in the successful manifest.
- Reuse availability knowledge only through an explicit state path outside the repository paired with one nonblank orchestration run identifier. The runner accepts only its exact bounded schema, rejects symlinked targets or ancestors, and uses directory-file-descriptor reads and atomic replacement so target or parent swaps are not followed.
- Availability state stores only one allowlisted reason code per bounded model name. Once a preferred or fallback model is recorded unavailable, skip another start of that model in the same run; never reinterpret remembered unavailability as an implementation, semantic, or validation result.
- Initial candidate manifests contain parent-produced bounded telemetry: attempt and total runner durations, actual model starts, current availability failures, skipped known-unavailable starts, candidate generations, full-validation count, and the selected risk and ambiguity. Durations are finite and nonnegative; custom workers record one attempt duration and zero model starts. Never place prompts, raw output, environment values, or credentials in availability state or telemetry.
- When parent review rejects a localized part of a candidate, use `scripts/run-sandboxed-plan-worker.py correct` with the in-progress plan, verified prior manifest, and a bounded parent-authored brief outside the repository. Do not regenerate the complete plan merely because review rejected the candidate.
- A correction verifies the prior HEAD, plan and patch digests, unchanged scope, normalized paths, symlink ancestry, clean source, and apply preflight before it starts. It applies the verified prior patch only in a fresh `--no-hardlinks` clone, mounts the copied brief read-only, hides prior artifacts and authentication state, and emits one aggregate patch against the original HEAD through the ordinary admission checks. The rejected patch never touches the source.
- Preserve bounded lineage digests for the prior manifest, prior patch, and brief plus a consecutive correction round. Allow at most two correction rounds; missing or skipped lineage and a third correction fail closed and require strategy change. Reuse the same run-bound availability state, and allow model fallback only for a new bounded availability error, never for review rejection, semantic failure, or validation failure.
- Candidate generation and correction do not run plan validation. After deterministic admission, parent diff review and critical-invariant review must finish before the parent explicitly authorizes `scripts/run-sandboxed-plan-worker.py validate` in a fresh credential-free, network-isolated review clone. Run optional `focused_validation` commands for the admitted slice first; existing plans without that list have no focused command. Run the authoritative `validation` list exactly once only when the candidate is otherwise acceptable.
- When authoritative validation fails, record `diagnosis_required` from its bounded validation report before any other lifecycle operation. The failure record binds the unchanged plan and source HEAD, execution-lifecycle digest, report digest, failed-operation digest, and observed exit status. Candidate mode additionally binds the exact failed candidate lifecycle, manifest, patch, and writable-attempt identity; parent-direct mode must not claim candidate artifacts. While stopped, allow only parent-owned read-only reproduction and append-only diagnosis evidence; reject runner, completion, archive, and repair-plan gates. Each of at most three diagnosis attempts requires a fresh independent-review receipt and reproduction-evidence digest. Only `confirmed` evidence may name one affected invariant and proceed to the existing repair classification; `inconclusive` or `disputed` evidence remains stopped. Store no command body, raw output, environment value, or credential in the execution ledger.
- Validation commands come from the unchanged committed active plan and the parent runner. Declare every project-specific transitive test/build helper in optional `validation_authority_scope`; the runner combines it with generic test, manifest, dependency, hook, Git/CI, and validation selectors and rejects a candidate that changes any authority path. Route such a slice to bounded parent implementation and independent review. Run each command in a separate fresh clone so one command cannot weaken a later command. Candidate product code may execute only inside the disposable review clone; validation must not gain credentials, network, source-write, external-write, authorization, or destructive authority. A failed focused or authoritative command stops acceptance and does not trigger model fallback.
- `validation_witness_schema: 1` marks a new or materially updated integration lane. Its `validation_witness_map` binds every acceptance item, in source order, by `sha256:<acceptance-bytes>` to its earliest parent-owned witness. A pre-schema project-owned integration plan remains readable only while its exact bytes and acceptance digests match one successor record in its existing versioned replan contract and that contract's source archive remains terminal `replanned`; field absence alone never proves legacy provenance. A `static` entry may name only `resolved-context-files`, which verifies normalized, non-symlink context paths and the terminal status of checked or replanned plan inputs. A `focused` entry must name an exact `focused_validation` command. An `authoritative` entry must name an exact `validation` command that is absent from `focused_validation` plus one bounded `authoritative_only_reason` explaining why no narrower safe preflight exists. Reject missing, duplicate, reordered, stale, unknown, unrelated-static, or late mappings before candidate execution. The map describes first evidence only and never removes, reorders, or weakens the authoritative suite.
- `validation-witness-migration-provenance-schema: 1` identifies only the canonical JSON snapshot at `.project-agent-workflow-migration/validation-witness-provenance-v1.json`. The v1.4.5 before-update migration may create it once from a clean committed Git root whose managed orchestration policy does not yet contain this marker. The snapshot records the source commit; committed Copier-answer and pre-update policy digests; and, for each pre-schema `in_progress` integration successor, the normalized plan path and digest, source-ordered acceptance text and digests, authoritative validation sequence and digest, schema-1 replan-contract path and digest, and terminal `replanned` source-archive path and digest. Inputs come from the one fixed commit as non-symlink regular Git blobs bounded to 256 KiB per plan and policy, 1 MiB per contract, 64 KiB for Copier answers, 64 integration plans, and a 512 KiB snapshot; HEAD and clean state are rechecked before exclusive publication. One original live guardian holds a 256-bit capability whose capability commitment binds the repository identity, source commit, snapshot digest, attempt id, and protocol version without storing the capability in the snapshot or mode-0600 Git-local attempt state. The guardian publishes that state through `prepared`, writes the exact snapshot, and reaches `pending` only after its mode-0600 Unix socket is listening; its lifetime is positive and no greater than the one-hour expiry bound recorded in the attempt state. The matching after-update stage requires the installed policy marker, unchanged committed HEAD, byte-for-byte snapshot reproduction, matching repository identity, and the confined Unix socket path to remain a socket with stable device/inode/change-time while connecting. The socket pathname is not identity evidence; a fresh 256-bit challenge-response opens the durable capability commitment and verifies a keyed proof from the same live guardian. After a valid consume acknowledgement, that guardian rechecks the marker, deadline, snapshot, and pending state, then durably transitions `pending` to `consumed` and returns a final keyed proof. If the final response is lost, only the same live guardian may resume that same consumed attempt; `consumed` remains terminal after the guardian exits and cannot be recovered or replayed. Permit `recovering` only before the policy marker exists and after the guardian lock proves the original guardian is no longer live. Recovery requires the unchanged clean source plus only its expected snapshot publication when present, the same repository identity, source commit, reconstructed snapshot, and an allowed bounded prefix during interrupted `prepared` or `recovering` publication; it moves a complete `prepared` or `pending` attempt to `recovering` before removing the stale snapshot, socket, lock, and state, and grants no compatibility authority. Expiry rejects after-stage authorization but permits this verified pre-boundary recovery. Reject missing, stale, unsafe, forged, cross-clone, consumed, or replayed after-stage evidence and reject symlinked or hard-linked regular-file evidence; reject a socket path that is not confined or changes type or device/inode/change-time while connecting. Preserve the migration-owned snapshot and consumed Git-local state across later non-destructive updates, but never count either as product acceptance evidence or as a validation witness by itself. Copying repository and Git-local files without the original live guardian fails; an unrestricted same-user actor that can replace every local process and file is outside this guarantee.
- Before a plan uses `npm run` validation, the parent runs `run-sandboxed-plan-worker.py prepare-dependencies --output-dir <new-external-directory>` against a clean repository with its project-approved `node_modules`, then passes the emitted manifest to `validate --dependency-snapshot <manifest>`. The project must commit `.node-version`; validation accepts only a host Node/npm runtime whose major matches that tracked file, copies only the resolved Node executable and npm package tree into parent-private temporary storage, omits npm-tree symlinks that point outside that runtime input, and records the actual version plus executable and npm-tree digests. It executes the private Node and npm CLI directly, provides verified private `npm` and `npx` launchers for nested scripts, and mounts only that minimal private runtime read-only instead of exposing its host installation root. Preparation creates the dependency directory as runner-owned mode `0700`, requires the installed package records to match `package-lock.json`, copies the dependency tree outside the repository, and records its complete digest. When browser-backed validation is required, the parent may add explicit allowlisted Playwright directories with repeatable `--playwright-browser-dir <external-browser-directory>`; preparation copies them under the digested `node_modules/.playwright-browsers` tree and never exposes their host source paths. Validation rechecks the package, lockfile, source HEAD, and tree digests, copies the verified tree into parent-private temporary storage, and mounts only that private copy read-only into each network-disabled fresh clone. Each validation command receives fresh writable scratch overlays only at `node_modules/.vite` and `node_modules/.vite-temp`; those overlays hide snapshot cache content, are not shared between commands, and cannot modify dependency packages or the verified tree. This proves which reviewed local tree and runtime were supplied; it does not independently establish registry provenance for the original installation.
- Reject a split npm installation whose private package copy cannot run by itself; install or select a self-contained Node/npm distribution matching `.node-version` instead of mounting undeclared sibling module directories.
- Bind every candidate to a locked parent-owned lifecycle ledger outside the repository. The ledger permits one current lineage leaf, rejects correction replay or forks, records cumulative bounded counters, consumes a validation attempt before its first command, requires focused success when declared before one authoritative attempt, and requires authoritative success before a one-time apply. Enter `applying` before source mutation; if final ledger persistence fails, use `finalize-apply` only after its isolated-index comparison proves that the source worktree exactly equals the verified patch. Apply only the patch bytes read and verified once; never reopen the candidate pathname after digest verification.
- One slice permits at most one initial generation and two isolated corrections. After the second rejected correction, record a strategy-change decision: split the invariant, change an otherwise qualified writable profile, or use bounded parent implementation. Parent implementation is allowed only for inseparable high-judgment work or exhausted correction budget, with explicit write scope, clean-worktree checks, no authority expansion, independent change review, and the same authoritative validation. Final interpretation, authorization, validation acceptance, commit, release, and completion reporting remain parent-owned.
- A strategy change is not an invitation to weaken the task. Mark the current plan `replan_required` and stop further candidate generation, correction, validation, apply, completion, and archival when scope/spec/security boundaries drift, more than one independently validatable invariant remains coupled, authoritative validation exposes a change that requires reconstructing source-plan boundaries, methods, validation authority, or acceptance mapping, the candidate correction budget is exhausted, or two parent-direct remediation rounds still leave a High or Medium finding. Preserve the source HEAD, plan digest, normalized acceptance digests, accepted safety conditions, committed work, and dirty product paths. Reconstruct only plan boundaries, ordering, implementation methods, and validation methods; a requirement change needs separate explicit user authorization. Resume only through a parent-admitted successor and integration contract. Elapsed time is telemetry and a checkpoint signal, never a semantic failure criterion.
- For one independently repairable defect, require bounded write and validation scope, one affected invariant, unchanged source-plan scope, validation authority, invariant boundaries, source acceptance and safety conditions, unchanged external-effect authority, a repair-evidence digest, and an independent-review receipt. Record `repair_required`, stop the affected execution run before any further operation, keep the source plan and index `deferred`, and create a separate bounded repair plan without copying acceptance or creating a replan contract. After the repair is checked, revalidate every unchanged input, return the source plan and index to `in_progress`, and initialize a fresh plan digest, source HEAD, candidate lifecycle, and execution ledger. Never relabel requirement, authority, or security-boundary drift as an independent repair.
- Initialize a parent-owned `plan-execution-state.py` ledger outside the repository for high-risk or correction-capable execution. Bind it to the run id, plan and primary-invariant digests, source HEAD, and a digest of the candidate-lifecycle identity. Record only bounded event ids, modes, counters, reason codes, invariant, repair-evidence and review-receipt digests, validation counts, lifecycle digests, monotonic timestamps, and finite elapsed telemetry. Parent-direct review and repair-classification events require an independent-review receipt. Classify a well-formed negative condition and enter its hard-stop state under the same exclusive ledger lock. Event replay, earlier-event rewriting, malformed counters, and stopped-state continuation fail closed. Pass `--plan-execution-state` to every candidate runner operation so `repair_required` and `replan_required` block before worker prerequisites or source mutation; never reopen a stopped ledger run.
- Use `plan-execution-state.py review --candidate-manifest <manifest>` for a staged candidate review. Fully reverify the runner manifest, patch, worker contract, completion receipt, process result, applicability, and scope before deriving the review target and review-budget identity from the current open attempt id, verified candidate-manifest digest, and admitted patch digest. Bind the review packet to that verified worker receipt and every current `required_specs` digest. Mutable lifecycle serialization may prove admission or apply state but cannot reset the budget. Require accepted closure to match a recorded review identity whose latest round has no High or Medium finding. For parent-direct work, derive the target from the plan write-scope diff and require the checked descendant commit to contain no out-of-scope path, match the latest reviewed patch, and use only receipts for that final target.
- Create one external reviewer session registry with `plan-execution-state.py registry-init`, then pass `--reviewer-registry` to every review, checkpoint, and checkpoint claim in the numbered-plan chain. The registry is canonical append-only JSONL at one bound path, stores only reviewer-session, execution genesis, and bounded event identity digests, rejects copied paths and session reuse under one exclusive lock, and permits an exact repeated admission only to recover a crash between registry append and ledger persistence. Bind each inbound checkpoint into the child ledger under a distinct event type. Checkpoints carry the registry id, path digest, event count, and event-chain digest; they never copy an accumulated reviewer list.
- For an already issued schema-1 checkpoint, run `plan-execution-state.py migrate-checkpoint` with the predecessor ledger, canonical registry, every recorded review receipt in ledger order, and the subset that produced the checkpoint reviewer list. The migration verifies the legacy digest and issuance, rejects an already claimed checkpoint, backfills every reviewer admission under its original event and execution-genesis identity, emits a schema-2 checkpoint, and appends one linked migration event without rewriting the old checkpoint or issuance. A boundary with no review events uses empty receipt lists.
- Reserve normal ledger capacity for checkpoint emission, checkpoint claim, and successor claim before writing a schema-2 checkpoint. A full legacy ledger may exceed the ordinary event budget only through the ordered compatibility suffix of migration, checkpoint claim, and successor claim.
- `predecessor_acceptance` means the exact accepted predecessor closing transition and its matching plan, candidate, accepted-source commit, and event digests required before a dependent writable attempt can start. Initialize a dependent ledger with `plan-execution-state.py init --predecessor-state <accepted-ledger>` and pass the same proof to the first runner call as `--predecessor-plan-execution-state`. The start transition takes the predecessor lock, verifies that its accepted-source commit is an ancestor of the current clean source HEAD, and appends one successor identity claim before opening the child attempt. The same claim may recover the same child after a crash, but another child cannot consume it; reject a missing, rejected, rewritten, substituted, stale, unrelated-source, or already-claimed proof.
- `successor_claimed` means the append-only predecessor-ledger event that consumes one accepted leaf for one exact child execution genesis identity. It permits idempotent recovery of that child only and rejects a second ledger whose plan, source, lifecycle, predecessor proof, or other genesis input differs.
- `writable_attempt_started` means the append-only event that exclusively opens one identified writable attempt in a dependency chain. Before the event, recheck the ledger genesis identity against the exact plan bytes, primary invariant, and source HEAD. Bind its unpredictable `plan_execution_attempt_id` through the freshly derived worker contract, parent-produced completion receipt, candidate manifest, and lifecycle state. After recording it, acquire the shared execution lease and recheck that the same id remains open before any worker prerequisite or invocation. Refuse a second open attempt and leave a crashed attempt open until the parent closes it. Independent bounded read-only helper work may overlap because it neither opens the writable chain nor acquires a global task lock; shared writable branches, checkouts, or helper integration remain prohibited.
- `attempt_closed` means the parent-owned append-only event that closes the current writable attempt and binds its candidate and review result. Acceptance requires the exact applied candidate lifecycle and manifest, the same ledger attempt id across contract, receipt, manifest, and lifecycle, and one clean descendant commit whose complete diff from the ledger source HEAD equals the admitted patch. The close records that accepted source commit for the successor ancestry check. A rejected or correction-requested closure requires `review_evidence_digest`, the primary affected-invariant digest, `review_author: parent`, and exactly one of `acceptance_unmet`, `out_of_scope_change`, `required_spec_missed`, `integration_contract_mismatch`, `focused_validation_failed`, `evidence_incomplete`, or `multiple_invariants_coupled`. `review_reason_code` identifies that bounded parent classification, not the concrete finding, and cannot waive a gate, clear a hard trigger, rewrite history, reset a counter, or authorize another start.
- Store predecessor, attempt, candidate, affected-invariant, review-evidence, and closing-event digests rather than findings, prompts, output bodies, environment values, credentials, patches, or repository content. A repeated review reason, `multiple_invariants_coupled`, a request for another correction after two corrections, or an existing hard trigger enters `replan_required`; a different bounded reason may proceed only through the next isolated correction within the unchanged budget.
- Use parent-produced counters for review rejections, correction rounds, focused validation, and authoritative validation in addition to the initial telemetry. Evaluation must retain median, edge, negative, and untuned holdout scenarios, no more than three implementation generations, at most one known-unavailable preferred start per run, one authoritative suite per accepted candidate, and zero unresolved High or Medium review findings. Require at least 30 percent lower median model starts and time to accepted patch and p95 time no more than 10 percent worse only from paired executions of the same fixed runner workloads; historical and rollout evidence for different plans must remain separately labeled and must not support a performance claim.
- Use `evidence_synthesizer` only for bounded comparison of multiple evidence sources, alternatives, or hypotheses whose result the parent can verify.
- Use `fast_scoped_worker` only when the expected edit and validation are known before delegation.
- Stop a fast worker when it encounters architecture, policy, security, authorization, destructive-operation, external-write, or scope-expansion decisions.
- Keep final judgment in the main session.
- Treat helper output as advisory until accepted through validation.
- Use durable handoff files only for cross-session transfer or staged work.
- Keep repeated helper prompt templates under `docs/plan/sub-agents/` when a project needs them.
- Use deterministic Stop hooks only as review prompts; they do not replace validation.

## Cost Gate

Use local execution for short deterministic commands, direct user clarification, final integration, validation acceptance, commits, tags, pushes, releases, and high-risk decisions.
Use helpers only when they return independently useful output and expected context reduction, parallelism, or review value outweighs coordination cost.
When helper output is used, include role, scope, and acceptance summary in the final report.

## Model Defaults

- Use `gpt-5.6-luna` with low reasoning for targeted repository exploration.
- Use `gpt-5.6-luna` with medium reasoning for current documentation research.
- Use `gpt-5.6-luna` with xhigh reasoning for `evidence_synthesizer`.
- Use `gpt-5.3-codex-spark` with medium reasoning for fast scoped coding and one-plan sequential implementation.
- For one-plan sequential implementation only, use `gpt-5.6-luna` with max reasoning as the single isolated availability fallback defined above; it is not the default helper profile.
- Use `gpt-5.6-terra` with medium reasoning for bounded implementation that includes ordinary judgment.
- Use `gpt-5.6-sol` with high reasoning for correctness, regression, security-sensitive, and policy-conflict review.
- Use a higher one-off effort only when the delegated task remains bounded and the prompt states why the default is insufficient.
- Reserve Sol with xhigh reasoning for exceptional final review of security, ownership, migration, or release risk.

## Luna Effort Selection

- Use low for targeted repository searches and existing-pattern lookup.
- Use medium for current documentation research and extraction of facts from several files.
- Use high as a one-off override when bounded read-only work must reconcile conflicting evidence or analyze a long context and the prompt states the expected quality gain.
- Use xhigh through `evidence_synthesizer` when the task compares multiple repositories, logs, specifications, implementation alternatives, or cause hypotheses and must report agreements, contradictions, impact boundaries, and unresolved questions.
- Do not use Luna for deterministic pass-or-fail commands, code edits, or final security, ownership, migration, release, or policy judgment.
- Do not define Luna max as a default helper profile. Its bounded sequential-worker availability fallback does not authorize final judgment; otherwise move the hardest final judgment to Terra or Sol unless a representative evaluation demonstrates a measurable Luna max benefit.

## Optional External Services

MCP, Linear, graph memory, and external CLIs should be modeled as opt-in modules. For each workflow, document whether operations are dry-run, read-capable, or write-capable. External writes require explicit user intent or a documented lifecycle command.

Generated repositories should use `docs/agent/SPEC_EXTERNAL_SERVICES.md` as the integration guide. It should name the credential source, connection metadata, write-capable commands, local fallback, and review boundary for each enabled service. Disabled services should still explain what must be added before the service can become required.
